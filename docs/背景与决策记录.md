# cairn 背景与决策记录

本文记录 cairn 的来历、用户的原话、各次讨论的结论，以及被否决方案的理由，目的是让接手的主控不用重新争论已经定下的事情。当前的设计以 [DESIGN.md](DESIGN.md) 为准，本文只说明"为什么是现在这样"。

## 3. 关键决定和理由

### 3.1 独立仓库（取代"Saddle 核心插件"和"Saddle 同仓独立组件"）

- **为什么不做 Saddle CorePlugin**：
  - 记忆的调用方是任意终端里的 agent hooks，不是 Saddle 主控。
  - CorePlugin 现有的设计只能在 TUI 里启用；插件停用后，宿主在进入插件之前就以 125 拒绝调用。
  - 现有资源安装器只管技能目录。
  - 这些都能补上，但补上的东西只有记忆一家在用。主控接受了这个判断。
- **为什么也不放在 Saddle 同仓**：
  - Corral 能当先例，是因为 Saddle 时时刻刻在调用它，而且用户要求统一安装。记忆不一样，Saddle 首版根本不调用它。
  - 同仓唯一的好处是共用构建和打包。
  - 现在还没写代码，这时拆最便宜。以后再拆，要迁移历史和打包，hook 的安装路径还会变。Codex 的信任绑定在 hook 定义的哈希上，路径一变，用户就得重新信任一遍。
  - 依赖边界放在两个仓库里，物理上就隔开了，不用靠自觉维持。
- **代价**：构建、安装、版本、开发流程都要单独维护。首版只在本机从源码安装，不随 Saddle 打包，避免两个仓库的构建又绑在一起。

### 3.2 存储：本机，SQLite 为主，Markdown 只导出

- 首版的难点在"状态"，不在正文：每个回合最多续跑一次、同一事件重复送达要去重、多个 agent 同时写、加载时找出各来源最新的可见记录。这些用 SQLite 的事务、唯一约束和查询来做，比自己管文件锁可靠。
- **代价**：
  - 数据库不能直接打开阅读，要通过命令看；
  - 删除时要开 `secure_delete` 并清理 WAL，否则原文会残留；
  - 表结构要带版本号；
  - hook 不能被数据库锁卡住。
- **跨机器**：SQLite 文件不能放进同步目录。"每条记录一个文件、只追加"的格式更适合同步，所以如果近期就要跨机器，会改成用文件存记录。用户答复暂时只用一台机器，因此选 SQLite，同时保留"ID 全局唯一、记录写入后不改"这两条，给以后留余地。
- **跨机器的本质**：记录只说明了另一台机器上当时的状态，代码本身不会跟着过来，所以跨机器接续离不开 Git 推送代码。这也是原来的 HANDOFF 加推送那套做法能跨机器的原因。

### 3.3 和 agent 是弱绑定

- 核心只认识自己定义的标准事件，每种 agent 一个薄适配器。只要能执行 shell 命令，就能用 `cairn save`。
- 自动化能做到什么程度，取决于 agent 提供哪些能力：
  - 有"会话开始注入"和"回合结束可续跑"两种 hook：全自动；
  - 只有项目指令文件：靠模型遵守；
  - 两者都没有：用户手动。
- 首版只承诺 Claude Code 和 Codex。其他 agent 每接一个，都要单独实测。

### 3.4 写入仓库外，项目明确采用

- 存在仓库外，保存就不需要提交和推送，直接去掉了用户痛点里"提交+推送"那一步。
- 全局安装 hooks，不等于每个项目都可以记录：只有用户 adopt 过的项目才生效。
- 现有项目规则（例如 Saddle 的 HANDOFF 规则）在用户明确调整之前保持不变。

### 3.5 保存触发：每个回合确认，最多续跑一次

（2026-10-13 起被 3.9 取代，下面留作历史。）

- 最早的设想是"每 K 轮或 Git 有变化时提醒"。被否决，因为它覆盖不到"只讨论一轮就正常退出"，而这正是用户最初的痛点。
- 曾设想单独做一个"已考虑保存"的标记。被否决，因为程序没法验证它。现在的"确认"同样只是模型自报，文档里明说了这一点，没有把它当成更强的保证。
- 曾提议让 agent 在每条回复里写记忆块或"无新内容"标记，由 Stop hook 读出来保存。被否决，因为会破坏"只回一行""严格 JSON""最后一行写 DONE"这类输出约定，也等于把交接仪式搬进了每一轮回复。现在走受限的 `cairn save`，具体的写入传输由第一阶段实测决定。
- 判断是不是续跑，只依据工具提供的字段（`stop_hook_active`、回合 ID），加上本地按唯一键去重。不假设"上次拦了，下一次 Stop 就是续跑"，也不假设同一会话的 hooks 一定串行。

### 3.6 缺口只报告观测到的

- Stop 计数看不到在 Stop 之前就中断或崩溃的回合；没观测到会话结束，也可能只是会话还在运行。所以只报事实，不推断。
- 不为补缺口去读会话记录（隐私问题，而且格式不稳定），也不另外调用 LLM 做摘要。（2026-10-13 起这一条改了，见 3.9。）

### 3.7 多写者与取代

- 只显示最新一条，会把另一个会话里不同任务的进展藏起来。所以各来源并列显示，冲突也并列。
- 不允许任何形式的取代的话，记录会无限堆积；允许自动作废，又会误伤。最后定为显式取代：只能点名当前上下文里注入过的具体 ID，必须同项目、同工作线，不能批量；被点名来源之后写的新记录不受影响；保留折叠提示，可以恢复。

### 3.8 记录不是授权

接续记录只提供方向和背景。下一个会话仍然要按用户本轮的要求行事；"用户原话"一栏是模型转述的，可能有误。

### 3.9 保存改由旁路模型写摘要（2026-10-13，取代 3.5 的做法）

试点里用了几天之后用户提的。原话（2026-10-12、10-13，对 cairn 仓库的主控）：

- "我发现一个问题，不会是每一个对话都会被记录吧？因为我发现现在已经记录了7跳了，短短8分钟"
- "对，现在首要的问题就是记得太频繁了。但是handoff的问题在于，只要我不主动handoff，就不会记。对吧？这变成俩极端了"
- "我同意旁路模型这个路线。现在的路线记得太多了，会造成混乱"
- "存的太频繁会导致两个问题，1: cairn的记录太多 2: 存的太频繁会造成模型存这个的也频繁感觉会耗费模型token也会感觉变慢。"
- "用codex做摘要。不要使用claude"
- "cairn save可以留着，但是不像现在这么调用。"

为什么这样定：

- 两个极端的根子是同一件事：没人知道哪个回合是最后一个。3.5 的办法是把每个回合都当成最后一个，让会话里的 agent 每回合写一次，结果是记录太多、每回合都慢一点。调研（`调研/会话接续的写入时机.md`）里唯一不需要知道"哪个回合是最后一个"的做法，是程序读会话内容、另一个模型事后提炼。
- 比过、没走的两种原料来源：
  - **压缩 cairn 已有的记录**（用户提的：照旧每回合存，到时机拿库里的记录调旁路模型写摘要，再把用过的记录收起来）：只解决记录太多，agent 仍然每回合要存。
  - **hook 留底**（hook 存下 `prompt` 和 `last_assistant_message` 当原料）：agent 不用存，但一个回合做很多事时只有首尾两句，回合没正常结束就什么都没有。用户："如果是任务型的，我一个回合里面做了好多任务，这个怎么搞？"要补上只能再挂每次工具调用的 hook，等于自己重抄一份会话记录。
- 所以读工具本来就写在磁盘上的会话记录。两次实测（`调研/旁路摘要可行性实测.md`、`调研/回合中途被杀的会话记录实测.md`）确认：拿得到；调已登录的 `codex exec` 写得出六节摘要；回合做到一半被杀时，杀之前做完的部分在记录里。
- 什么时候写，10-13 先选了"下一个会话开局时同步写"而不是"会话结束时"：实测里 Codex 被 `corral stop` 关掉时没有会话结束事件，两家被强杀时都没有，而 `corral stop` 是用户平时关 agent 的办法。开局时写，一个办法管住所有退出方式，也不需要后台进程。代价是开局多等一次，当时用户接受了。
- **10-13 看过并进 DESIGN 的稿子后，用户推翻了开局同步写**："但是agent开始的时候跑，然后我等几十秒，我接受不了"。改成后台写（2026-10-15 定）：回合结束时起一个脱离会话的等待进程，会话安静满 3 分钟、会话结束、或同一条工作线上有新会话开局时写；开局不等，写好的在用户下一次发话时补注入。这样仍然管住所有退出方式（没有会话结束事件的，靠安静 3 分钟或下一次开局），代价换成：刚关掉一个会话马上开新的，第一句话可能看不到它的摘要。用户原话（10-15）："3分钟可以，偶尔第二句才补上也能接受。"
- 用户 10-13 还问过两件，主控答了、用户没有反对：后台会不会有好几个进程各写各的（每个会话最多一个等待进程，靠占位和心跳）；同一个目录两个 agent 做不同任务（摘要一个会话一份不混，开局两份并排给出；补注入只补开局时已经停下的会话，并排还在干的不补进来）。
- 这推翻了 3.6 里"不读会话记录、不另外调用 LLM 做摘要"，也推翻了 DESIGN 的 D12。隐私上的代价用户知情：对话内容的摘录会交给 Codex，Claude Code 的会话也是。用户确认过这只是读本机的文件，不牵涉 Claude 的模型，没意见。
- 3.5 里否决过的"每 K 轮或按时间提醒"仍然不做。
- **2026-10-15 补：值不值得写由旁路模型判断**（DESIGN §8.8"不用写"，P1-11）。试用 0.4.0 时用户问："假如我开了新session，但是就是聊没什么意义的话，会不会也会在关闭的时候更新？"当时会：只要有一个回合就写，闲聊的会话排在注入最前，把有用会话的全文挤成一行。用户："cairn这个旁路服务要判断是不是有效？值不值得进cairn的数据库。"主控提议在要求里写一份"什么算值得"的清单，用户没要："不能让旁路模型判断值不值得进新的cairn吗？"所以要求里只给一句标准，由模型自己判断。判错了怎么补，主控提议让 `cairn summarize` 跳过判断强制写，用户选了"不单独处理"。

### 3.10 项目的账：长期记忆替代 HANDOFF（2026-10-15）

- 起因：会话摘要只管“上次停在哪”，挂了几天的悬而未决会掉出注入，所以 HANDOFF 还得手写，cairn 只解决了一半。用户：“其实我想把现在handoff抽到项目的长期记忆中。这样就全了，cairn有会话级别的记忆，也有长期的记忆。”“我的想法就是完全替代掉handoff。”
- 两层分开：用户：“cairn要同时设计会话级别的短期记忆和长期记忆，而不是用一个表。”两者的单位、范围、寿命、更新方式、注入规则都不一样，硬放一张表会缠在一起。
- 谁写：旁路模型自动记，不设确认（用户“2 行”）。主控比过“模型只提议、用户确认才算”，代价是用户要常来点，违背“用户不用为记忆做事”；选了自动，靠依据、可恢复、看得到最近变动来兜底。
- 记账和写摘要分两次调用（用户“3 分两次”）：一次省调用，但两份输出缠在一起。
- 注入总预算加到 9,000 字符（用户“4 加到9000”），没走的另一条是总量不变、账和摘要分着用。
- 不做导入命令（用户：“直接agent导入就行了。因为几个handoff还需要规整呢。”）。
- 一、二期合成一次开发，三、四期是使用和迁移（用户：“1，2是开发。3，4是使用”）。
- 10-11 的记忆系统设计草案（经验手册、跨项目共享）里“项目的账”这一块由本节取代，其余以后另议。逐条的决定和验收五条见[长期记忆设计草案](长期记忆设计草案.md)，权威设计在 DESIGN D13、§8.9。

### 3.11 cairn 只管项目里的记忆，全局记忆不归 cairn（2026-10-16）

- 四种记忆：用户：“我印象中，就是这四种记忆吧。会话记忆，长期记忆，全局记忆和经验沉淀记忆”。
- 被否决的做法：主控提议在 cairn 里存一本“不属于任何项目的账”做全局记忆，只收用户明确说“所有项目都这样”的话，由旁路模型记、开局在每个项目里注入。用户：“全局记忆不就是现在codex和claude配置目录下的agents.md/claude.md吗？”主控认同：那些文件是工具当作指令照做的地方，cairn 的注入只是“带来源的历史，不是指令”，权威性低一档；用户自己写，也免掉“写错一条污染所有项目”的风险。在 cairn 里另做一套是重复造轮子。
- 也没走的折中：cairn 从会话里认出“所有项目都这样”的话，提议改哪个全局文件，用户点头才改。用户没接这个，另提了下一条的做法。
- 定下的：用户：“我想的是，全局记忆就现在这个样子。但是是否可以在paddock的setting中显示出来各个agent的全局设定。而且可以切换到编辑。不管是claude的，还有codex和现在接入的所有的agent。你觉得如何？cairn从此只管项目记忆（短期记忆，长期记忆，经验沉淀）。”cairn 不读、不写、不同步全局文件；显示和编辑交给 paddock（10-16 已通知 paddock/main）。
- 代价：会话里说过的“以后所有项目都这样”，不会自动进全局设定，要用户自己去改。主控认为可以接受，用户没表态。
- 经验沉淀只管项目内，原来设想的“跨项目经验”随之不做。任务草稿在 `docs/任务/P1-19-经验沉淀.md`；权威设计在 DESIGN D14。

## 4. 参考过的外部做法

- Claude Code 自带的自动记忆：只在本机，按仓库保存，由 Claude 自己写，偏向长期偏好和学习，而且只有 Claude 能用。cairn 做的是跨工具的工作接续，两者互补。
- Anthropic 关于长时 agent 的工程文章：用进度文件加 Git 日志，新会话先读。这是靠提示词的约定，和用户现在的 HANDOFF 做法相近。
- beads（任务图加记忆，`bd prime` 负责注入）和 engram（Go 写的单个二进制加 SQLite，agent 主动保存，用 MCP 接入）：两者都印证了"agent 主动保存加开局注入"是常见做法。cairn 不做检索、任务图，也不用 MCP。
