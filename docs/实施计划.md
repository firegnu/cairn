## 阶段 1：能力实测（实施门槛）

### 目的

在本机真实的 Claude Code 和 Codex 上，确认 DESIGN 依赖的每一项 hook 能力确实可用，并选定写入传输方式。官方文档写了某项能力，不代表本机版本就支持；这一步也不能拿文档代替实测。

### 约束

- **不改用户的真实配置**：不写 `~/.claude/settings.json`、`~/.codex/hooks.json`、`~/.codex/config.toml`。注入 hooks 只用两种方式：
  - 会话级参数：Claude 用 `--settings <文件>`，Codex 用 `-c hooks.<事件>=…`；
  - 临时目录里的项目级配置：`<临时仓库>/.claude/settings.local.json`、`<临时仓库>/.codex/hooks.json`。
- **点信任会留下记录**：Codex 的项目信任、hook 信任，Claude 的目录信任，都要用户在界面上点。点了之后，工具会自己记下信任状态。实测结束后，主控要告诉用户去哪里清除。
- **只用合成材料**：临时 Git 仓库加合成的提示词。探针的日志只放在临时目录，不提交原始日志。提交进仓库的证据只摘录字段名和合成值。
- **不读真实数据**：不读真实会话记录、各工具自带的记忆，也不读 Corral 的事件文件。
- **开 agent 的规矩**：只开自己的 `cairn/test-*` agent，用完就 `corral stop`。不碰用户已有的 agent。

### 探针

先派一个小任务，做一个 Rust 写的探针程序 `cairn-probe`。它作为仓库里单独的一个 workspace 成员，阶段 1 结束后可以删掉。它只有三项功能：

1. `cairn-probe hook <claude|codex>`：把 stdin 收到的 JSON 追加写入 `$CAIRN_PROBE_DIR/events.jsonl`，并记下收到的时间。然后按 `$CAIRN_PROBE_DIR/plan.json` 的配置输出：
   - SessionStart：输出带唯一口令的注入文字；
   - Stop：第一次续跑、之后放行，或者一直放行；
   - 其他事件：不输出。
2. `cairn-probe save [--source ID] [--nothing-new]`：读取 stdin，写入 `${XDG_STATE_HOME:-~/.local/state}/cairn-probe/saves.jsonl`。这个位置在工作区之外，用来测沙箱。
3. 输出一律退出码 0。Stop 的 JSON 要符合两种工具的格式。

### 实测项

| 项 | 要确认什么 | 建议方法 |
|---|---|---|
| A 注入 | SessionStart 在 startup、clear、compact、resume 时是否触发；注入的口令模型能不能看到；6,000 字符的中文注入是否完整到达，Codex 设了 `additionalContextLimit` 之后呢 | 用非交互方式启动（Claude 用 `-p` 加 `--settings`，Codex 用 `exec` 加 `-c`），让模型复述口令。clear、compact、resume 用交互式测试 agent，由 `corral send` 发 `/clear`、`/compact` |
| B 回合与续跑 | Stop 输入里有没有 `prompt_id` 或 `turn_id`、`stop_hook_active`；返回 block 后是否只续跑一次；续跑时这两个字段各是什么值，回合 ID 变不变；用户中断时 Stop 会不会触发，Codex 的 Interrupt 呢；同一事件会不会重复送达；UserPromptSubmit 能不能可靠地标出回合起点 | 用 plan.json 让第一次 Stop 返回 block，看 events.jsonl 的顺序和字段。中断用 `corral keys` 给自己的测试 agent 发 Esc |
| C 写入传输 | 模型能否在回答之前调用 `cairn-probe save`，回答文字里不出现任何标记；Claude 在默认权限下要不要每次批准，用窄规则（例如 `Bash(cairn-probe save:*)`）能不能免批准；Codex 在默认 workspace-write 沙箱下能不能写进状态目录；会话关联（`--source`）可不可靠 | 交互和非交互各测一次。**不扩大沙箱，不开 bypass。** 结果要写清：哪些配置是必需的 |
| D 会话结束 | SessionEnd 在 `/exit`、正常关闭、`corral stop` 时会不会触发；在时限内能不能完成写入 | 看 events.jsonl |
| E 安装与信任 | 用户级 hooks 和插件 hooks 哪个更合适（Claude）；hook 文本不变、只替换软链接背后的二进制之后，Codex 是否还信任；改了文本是否需要重新信任 | 在临时项目的 `.codex/hooks.json` 里测；软链接放在临时目录 |
| F 与 Corral 共存 | 用 Corral 启动的 Claude（Corral 用 `--settings` 注入 hooks）加上项目级 hooks，两边是否都执行；Corral 启动的 Codex（`-c` 注入、bypass 信任）加上项目级 hooks 呢 | `corral start cairn/test-<名> --cwd <临时仓库> --label role=test -- claude`（Codex 同理）。用户需要通过 `corral attach` 点一次信任，再按 Ctrl-] 断开 |
| G 续跑对输出的影响（R4） | 续跑后最后一条回复变成什么；要求"原样再给出上一条最终回答"能不能保住"最后一行 DONE"和严格 JSON 这类约定；Claude 用 `-p` 时最终 result 是哪一条 | 用合成提示词，要求只回一行 JSON 或者最后一行写 DONE |
| H 环境开关 | hook 进程能不能继承 agent 的环境变量（决定 `CAIRN_DISABLE=1` 是否可行） | 带环境变量启动，让探针把这个变量的值写进日志 |

### 门槛与产出

- A、B、C、F 四项在**两种工具上都通过**，才进入阶段 2。D、E、G、H 不阻塞，但它们的结论要写进 DESIGN。
- C 项在某种工具上做不到时：停下，向用户报告具体限制和可选做法，由用户决定。不悄悄降级，也不改回"在回答里加标记"。
- 产出：
  - `docs/调研/第一阶段能力实测.md`：记下 `claude --version`、`codex --version`，每项每种工具的结果（通过、不通过或部分通过）以及证据摘录；
  - 按结论修订 DESIGN 的 §8.3、§9.1、§10、§14、§15；
  - 告诉用户哪些信任记录需要清除。
- 建议路由：这是"碰要害"一类的工作，因为它决定"自动"二字的边界。可以拆成"探针程序"（轻）和"实测与报告"（重），后者需要用户在旁协助点信任。

## 阶段 3：接入

| 任务 | 内容 | 依赖 | 建议验证 |
|---|---|---|---|
| 3a hook 适配 | `cairn hook <agent>`：解析和输出，接到 2c–2e；SessionEnd 在时限内完成；错误时放行并记日志 | 阶段 2 | 用阶段 1 摘录的合成 JSON 做夹具；未采用时不输出；`CAIRN_DISABLE`（若 H 通过）；两种工具的 Stop 输出格式 |

| 3c 安装方式 | `cargo install --path .`，或者一个只用 sh 或 Rust 的安装说明；README 写清安装、采用、卸载的步骤 | 3b | 在全新的隔离 HOME 里按 README 从头走一遍 |

阶段 3 完成后，用户在自己的真实环境里执行 `cairn install`，这一步需要用户明确同意。主控不替用户安装。

## 阶段 4：用户试点

- 由用户决定在哪些项目上 `cairn adopt`，主控不替用户选。
- 建议观察以下几点，作为下一步决策的依据：
  - 是否还需要提醒 handoff 或"读 handoff"；
  - 每回合确认带来的负担（延迟、权限弹窗）；
  - 续跑的频率，以及它对输出约定的影响；
  - 有没有把历史记录当成现状；
  - 被委派 agent 和脚本会话带来的成本。
- 试点结束后，再由用户决定其他项目（例如 Saddle）里现有的 HANDOFF 规则要不要调整。cairn 不自动修改任何项目的规则。
