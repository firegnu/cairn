## 1. 要做成什么

cairn 现在只记一种东西：这条工作线上次停在哪（接续记录）。它短命，新的顶旧的，开局全量注入。

要加的是**长期记忆**：不随某件活结束而过期、以后的会话还用得上的东西。它越积越多，所以要多解决三件事：每次注入哪些；哪些已经过时或当初就写错了；一个 agent 写的，别的 agent 该信几分。

| M2 | cairn 自己先不调用模型。提炼、整理借会话里的 agent 做。不连网、不读会话记录（D12 不变） |

### 1.2 往哪个方向长（草案）

单论“存和查”，这个领域已经很挤（调研 §1.3）。离 cairn 最近的 Engram 走的是同一条路（agent 主动挑着存、本地 SQLite、跨工具），而且已经有检索、按主题更新、冲突标注。cairn 不在这些上面和它比多。

cairn 围绕自己已有、别家少见的两样东西长：

1. **对照现场**。cairn 开局会拿记录和 git 的实际状态比。延伸到长期记忆：一条记忆依赖的文件没了、或者写下之后那个文件又改过很多次，开局就标出来。对着调研 §4 第 2 条“新的不等于对的”。
2. **来源和分量**。现在的纪律是“记录是带来源的历史，不是指令”（D7）。延伸到长期记忆：每条都带着谁写的、依据是什么、用户确认过没有；分量不同，注入时的说法不同，能传多远也不同。对着调研 §4 第 5、6 条“污染会延续、共享会扩散”“事实、偏好、规矩要分开”。

### 1.3 为什么不直接装一个现成的（草案）

- 现成项目多数靠 MCP 接入，或者要另起服务、配向量库、配模型。cairn 靠 hook 加一条 shell 命令，两种工具走同一条路，不用 MCP，不连网。
- cairn 已经有每回合一次的保存机会和开局注入，这两样是长期记忆最难保证的环节（调研 §3.1：“都能执行命令，还需要约定什么时候存、什么时候查”）。
- 上面两样差异点，在看过的项目里没有现成的。

这是主控的判断，没有装过那些项目做对比。

## 2. 记什么：条目（草案）

长期记忆的单位叫**条目**：一条只写一件事，短，可以单独更新、单独作废。它和接续记录是两种东西，分开存、分开注入。

| 种类 | 是什么 | 例子 |
|---|---|---|
| 事实 | 这个项目是什么样的，看代码不容易看出来的 | “save 的测试因积压回归要跑 50 秒左右” |
| 经验 | 做某类事该怎么做、别怎么做，是做过之后才知道的 | “并行跑多个测试时 git 超时 2 秒会偶发失败” |
| 偏好 | 用户要怎样 | “派活优先给 Codex” |

**规矩不归 cairn 管**。必须遵守的规则留在 `AGENTS.md` 这类进版本库、由人维护的文件里。cairn 的条目不管是哪一种，都不是指令。一条偏好稳定了、用户想让它变成规矩，cairn 可以把文字导出来，由用户自己放进 `AGENTS.md`；cairn 不自动改任何项目的规则（DESIGN §13 这一条不变）。

每条条目带这些属性：

| 属性 | 内容 | 用处 |
|---|---|---|
| 作用域 | 项目（默认），或全局 | 全局的在所有已采用的项目里都注入（第 6 节） |
| 来源 | 哪家 agent 的哪个会话写的、什么时候 | 和接续记录一样 |
| 依据 | 用户说的 / 自己观察到的 / 推断的 | 注入时写出来，让读的 agent 知道该信几分 |
| 确认 | 未确认 / 用户确认过 / 用户自己写的 | 决定注入时的说法和能传多远（第 3 节） |
| 锚点 | 可选：这条依赖仓库里的哪些路径，写下时的 HEAD | 对照现场（第 4.2 节） |
| 标题和正文 | 标题一行，正文有长度上限（建议 1 KiB） | 开局只注入标题，正文按需查 |

条目和接续记录一样写入后不改：要改就写一条新的取代旧的，或者由用户更正、撤回、恢复、删除。这些动作沿用现有的规则（DESIGN §8.5、§8.2 第 7 步）。

## 3. 分量：确认和传播（草案）

原则：**一条条目能影响多大范围，取决于用户确认到哪一步。**

| 确认级别 | 怎么来的 | 本项目里 | 跨项目 |
|---|---|---|---|
| 未确认 | agent 写的，用户没看过 | 注入，标“未经用户确认” | 不传 |
| 用户确认过 | 用户对某条执行了确认 | 注入，排在前面 | 用户把它设成全局才传 |
| 用户自己写的 | 用户用命令直接写的 | 同上 | 同上 |

- 哪一级都不是指令或授权。抬头的规则文字照旧：和用户本轮要求冲突时以用户为准。
- 不同来源写的条目互相矛盾时并列显示（D9 的做法），cairn 不裁决谁对。由 agent 声明取代，或者由用户处理。
- 确认是为了挡住“写错的经验持续带偏”和“污染扩散”。它也是用户的负担，所以确认的入口要尽量省事（第 7 节：paddock 面板上点一下）。**未确认的条目在本项目里注不注入，是明天要定的第一个问题**：注入则省事但有被带偏的风险，不注入则安全但每条都要用户点。

## 4. 读：注入哪些，怎么对照现场（草案）

### 4.1 开局注入

做法是调研里几家都在用的那种：开局只放一个小索引，正文让 agent 按需查。

- 接续记录照旧，预算优先给它。
- 另留一小段预算（建议 1,500 字符起，可配置）给条目索引：每条一行，写种类、标题、ID，以及“未经用户确认”“锚点已变”这类记号。
- 排序是确定的规则，不用向量检索：用户确认过的在前；偏好在事实和经验之前；同级里最近被用过或写下的在前。
- 放不下的不删，只是不进索引，末尾写一行“另有 N 条，用 `cairn recall` 查”。
- 正文按需查：加一条只读命令 `cairn recall <关键词>`，用 SQLite 自带的全文检索（FTS5）。它是 agent 可以用的第二个命令。

### 4.2 对照现场

对进了索引的条目，开局时核对它的锚点：

- 锚点路径不存在了：标“依赖的文件已不存在，可能过时”。
- 路径还在，但写下之后被改过：标“写下之后该文件改过 N 次”。

只报观测到的事实，不替 agent 判断这条还对不对（和 D8 同一个原则）。git 调用照旧设超时，一次开局核对的条数有上限，超了就不核对、照常注入，保证 hook 不被拖慢。

没写锚点的条目不核对。偏好通常没有锚点。

## 5. 写和改（草案）

### 5.1 谁写、什么时候写

- **agent 在会话里写**。每回合仍然只有一次必须的确认（D6 不变），不加第二次强制调用。agent 觉得有值得长期记下的，另外调用一次写条目的命令。
- 写的入口：新命令 `cairn remember`（种类、依据、锚点走参数，标题和正文走 stdin），和 `cairn save` 一样只写暂存区，由 hook 和用户命令收取。**用单独的命令，还是塞进 save 的正文里，明天要定**：单独的命令语义清楚，但 Claude 那边要多放行一条规则（要改用户的真实配置，升级时得用户同意）；塞进正文不用多放行，但要解析自由文本，容易出错。
- 什么该记，写在抬头的约定里，大意：以后的会话也用得上、不随这件活结束而过期的才记；用户的纠正和偏好最该记；一条只写一件事；写明依据；看代码就能知道的不记。
- **用户自己写**：同一条命令，由用户执行，确认级别直接是“用户自己写的”。

cairn 不读提示词和回答（隐私规矩不变），所以它自己发现不了“用户刚纠正了 agent”，只能靠 agent 自觉。这是走“agent 挑着存”这条路的固有代价：会漏记。

### 5.2 经验手册怎么演化（M3）

三个动作，都不需要 cairn 调用模型：

1. **逐条更新**。agent 发现某条不对或不全，写一条新的取代它（只能取代注入给过自己的，规则同现在的接续记录）。旧的折叠、可恢复。
2. **使用反馈**。agent 在每回合那一次 `cairn save` 上可以顺带标记：这回合用上了哪条、发现哪条是错的。cairn 只记数。被标错的条目在索引里带记号，并进入待整理清单。
3. **整理**。cairn 按确定的条件列一份待整理清单：锚点失效的、被标错的、长期没确认的、标题相近疑似重复的。用户想整理时，让一个 agent 照这份清单逐条处理（取代、撤回），或者自己在命令行、paddock 面板上处理。**整理由用户发起**，cairn 不在后台自动做。

没人用、也没确认的条目不会被自动删除，只是排不进索引（沉底）。真要删由用户删。

## 7. 和别的程序结合（草案）

沿用 DESIGN §7.1 的“只加不改”：

- 新增可依赖的输出：条目列表、单条条目、待整理清单的 JSON。
- 新增可调用的动作：确认一条、撤回一条、设成全局。

## 9. 存储（草案，实现任务定稿）

表结构升到版本 3，只加表，v1、v2 的表和数据不动。条目不放进 `records`：那张表每行都绑着工作线和现场事实，条目是项目级或全局的。

```sql
CREATE TABLE entries (
  id TEXT PRIMARY KEY,                               -- ULID
  project_id INTEGER REFERENCES projects(id),        -- NULL 表示全局
  source_id TEXT NOT NULL REFERENCES sources(id),
  kind TEXT NOT NULL,                                -- fact / lesson / preference
  basis TEXT NOT NULL,                               -- user_said / observed / inferred
  title TEXT NOT NULL, body TEXT,                    -- 删除后 body 为 NULL
  anchors TEXT,                                      -- JSON：路径列表、写下时的 HEAD
  created_at TEXT NOT NULL, deleted_at TEXT);
CREATE TABLE entry_marks (                           -- 只追加：对条目做过的事
  id INTEGER PRIMARY KEY, entry_id TEXT NOT NULL REFERENCES entries(id),
  kind TEXT NOT NULL,                                -- confirmed / superseded / retracted / restored / made_global / used / wrong
  by_source TEXT, other_id TEXT, at TEXT NOT NULL);
```

全文检索用 FTS5 建在标题和正文上。要注意的一处：`cairn delete` 承诺删掉正文不留残余，全文索引里的副本也得一起清掉，这一条要有专门的测试。

## 10. 分期（草案）

每一期单独能用、单独能验，做完看试点再决定下一期。

| 期 | 做什么 | 做完能看到什么 |
|---|---|---|
| 一 | 条目的存、看、改：`remember`（或定下来的写法）、收取、list / show / 取代 / 更正 / 撤回 / 删除 | 条目能存进去、查出来，不注入 |
| 二 | 开局注入索引、`recall`、对照现场 | 新会话开局看到条目索引和“锚点已变”的记号 |
| 三 | 确认和分级、给别的程序用的公开约定 | 能确认；注入的说法随级别变；paddock 能接 |
| 四 | 使用反馈、待整理清单 | 经验手册能演化（M3） |
| 五 | 全局作用域 | 一条确认过的偏好在别的项目里也出现（M4 第二步） |

第一期开工前先做一次小的实测（和阶段 1 同样的道理）：第二个 agent 可用的命令，在 Claude 的权限规则和 Codex 的默认沙箱下是否都走得通。

## 11. 风险（草案）

| 风险 | 说明 | 打算怎么对付 |
|---|---|---|
| 每个会话更费 | 索引每次开局都占上下文，写条目是额外的工具调用 | 索引预算设上限；写条目不强制；试点时量开销 |
| 写错的经验持续带偏 | 这是长期记忆固有的问题 | 确认分级、对照现场、使用反馈、可撤回。只能减轻，不能根除 |
| 污染 | agent 把读到的网页、文件里的话当成经验记下来 | 依据一栏、未确认的不跨项目传。cairn 判断不了内容真假 |
| 漏记 | 靠 agent 自觉挑着存 | 接受。不改成全量采集，那要读会话内容 |
| 和自带记忆重复、打架 | 两套记忆各说各的 | 见第 6 节，待定 |
| 证明不了“记了有用” | 调研 §4 第 4 条，整个领域都没解决 | 试点时看使用反馈的计数；用什么判断，明天要谈 |
| hook 变慢 | 开局多了核对锚点 | 条数上限、超时、超了就跳过 |

## 12. 明天要定的问题

按重要程度排：

1. **未确认的条目在本项目里注不注入？** 主控建议：注入并标明“未经用户确认”，跨项目必须确认。
2. **agent 写条目用单独的命令，还是塞进 save 的正文？** 主控建议：单独的命令 `cairn remember`。
3. **确认这个动作放在哪？** 命令行一定有。主控建议同时给 paddock 面板留好约定，把它当主要入口。
4. **条目分事实、经验、偏好三种，够不够、多不多？**
5. **和 Claude Code、Codex 自带记忆的关系：并存不管、建议关一边，还是提供导入？** 主控建议：先并存不管，试点里看重复有多严重。
6. **派出去的 agent 要不要只读地拿到条目？** 主控建议：先不做，它们的规矩在任务文件和 `AGENTS.md` 里。
7. **试点时拿什么判断“记了有用”？**
8. **分期的顺序和第一期的范围对不对？**
