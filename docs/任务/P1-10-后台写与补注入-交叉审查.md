## 重点看

1. 触发条件：三条是否照 §8.8；主控审查里提的“恢复的会话带着旧的 `session_ended`”是否真会让每个回合都立刻写；同工作线新开局那条会不会被自己或无关事件误触发。
2. 占位和退出：每个会话最多一个在等；写完在同一事务里核对新事件、接着等或释放退出，会不会和刚结束的回合撞出“两边都以为对方会管”的空档（§8.8“写完之后”那条）；占位丢了不写。
3. 进程：hook 起进程后立刻返回，SessionEnd 在时限内；子进程真的脱离（`setsid`、`/dev/null`）、不继承 hook 的管道；SessionStart 在事务里起进程，事务回滚时会怎样；等待进程会不会永远不退出、越积越多。
4. 补注入：只补开局时已停下的会话、不补并排还在干的；同一版不重复补，新版照补；`injections` 和实际输出一致；没有可补的就不输出。
5. 禁用和未采用：带 `CAIRN_DISABLE=1` 或项目未采用时，hook 不起进程，`__wait` 不写。

### R1（必须改）：历史结束事件让恢复后的每回合立即写摘要

- **位置**：`crates/cairn/src/sidecar.rs:430–437`，尤其第 431 行的无时间限制 `EXISTS(... kind='session_ended')`。
- **问题**：同一来源只要结束过一次，之后 resume、UserPromptSubmit、Stop 都不会使这条结束条件失效；有新增内容时每次都会立即调用旁路模型，绕过 3 分钟安静窗口。这是主控留下的问题，已确认是核心触发规则的真实缺陷。
- **复现**：临时 Git 仓库、隔离 HOME/XDG_STATE_HOME、合成 transcript 和假 Codex。先送 SessionStart → UserPromptSubmit → SessionEnd，写成第一版；再对同一来源送 SessionStart(resume)，连续做两次 UserPromptSubmit → 增长 transcript → Stop。为固定调度，种入 hook 时用夹具占位阻止自动启动，随后清掉夹具占位，直接运行原二进制的 `__wait`；两次分别 **24 ms、24 ms** 就写成，摘要总数从 1 变成 2、3。两次都没有新的 SessionEnd、其他会话或 3 分钟静默，故不能由另外两条触发条件解释。
- **改法**：结束条件应反映当前这次运行是否已经结束；其后收到 SessionStart/TurnStarted 时，旧的结束事件不得再触发。保留历史事件，以接收时间及必要的事件顺序判断有效性，不用删除历史来修补。补上“结束后恢复、连续新回合不立即写；新的结束仍立即写”的直接回归。

### R2（必须改）：取消采用后退出不释放自己的占位，重新采用会漏启动

- **位置**：`crates/cairn/src/sidecar.rs:415–418`；关联 `Lease::heartbeat` 的第 71–81 行、`launch_waiter` 的第 118–119 行。
- **问题**：`heartbeat` 返回 false 既可能是占位被接手，也可能只是项目被取消采用。当前直接返回，事务回滚，自己的 `waiter_id/waiter_beat_at` 留在库里。若在旧心跳满 60 秒之前重新采用，Stop、SessionEnd 都把已退出的进程当成新鲜占位而跳过启动。此后若不再有 hook，就没有进程负责摘要；60 秒过期本身不会触发任何调度。
