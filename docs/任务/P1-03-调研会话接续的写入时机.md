## 要做的

上网查，写一份中文报告 `docs/调研/会话接续的写入时机.md`，回答用户的问题：别的系统有没有这个问题，有的话是怎么对付的。

**“这个问题”指什么**：给 coding agent 记“这件活上次停在哪”（会话状态、交接摘要这一类，不是长期的事实和偏好），什么时候写。现在看到两头：

- **每个回合都写**。不会漏，但记得太勤。cairn 现在是这一头：每个回合结束前，agent 要么写一条完整的记录，要么确认没有新内容；同一个会话写了几次，就是几条记录。
- **等人或 agent 觉得该写了才写**（手动的交接文件、“结束会话前存一条摘要”）。省，但没人想起来就一直不写；会话突然结束（关窗口、崩溃、用户直接走了）时，最后一段就没了。

两头的根子是同一件事：agent 不知道哪个回合是最后一个。

**查两类对象**：

1. 上一份调研覆盖过的那几家：Claude Code、Codex、Gemini CLI、Engram、beads、Claude-Mem、Mem0 / OpenMemory、Graphiti / Zep、Letta Code。只补这一个问题，上一份写过的不重复。
2. 专门做会话接续、交接的做法和工具：各家 agent 自带的（恢复原会话、压缩上下文时的摘要、交接类的命令）；社区里专做接续、handoff、session continuity 的项目；有影响的厂商工程文章。挑有代表性的，不用求全。

**每个对象尽量说清这几件事**（查不到就写查不到，不要猜）：

- 它记不记会话状态；记的话，和长期条目是不是分开的。不记的话，接续靠什么。
- 谁写、什么时候触发：每回合、会话结束、压缩上下文前后、隔一阵或满足某个条件时提醒、会话过后在后台处理。触发靠的是什么：hook 事件、指令文字，还是后台进程。
- 会话突然结束时，最后一段会不会丢，有没有兜底。
- 同一个会话里多次写：每次新增一条，还是更新同一条。旧的怎么显示、怎么清。
- 写的代价落在谁身上：占 agent 的回合、另一个模型，还是纯程序。要不要读会话内容或用户的提示词。
- 有没有用户反映“记得太勤”或“漏记”（issue、讨论区），项目怎么回应的。

最后单列一节：有没有谁两头都顾住了（不漏，也不勤），怎么做到的、付了什么代价；没有的话，各家卡在哪。

**写法**：

- 开头一段总览，先给结论，再展开。
- 每条事实后面给来源链接，并写上你查看的日期。区分“我打开原文看到的”“别处转述的”“我的推测”。
