## 1. 为什么改

用户 10-12：

- “我发现一个问题，不会是每一个对话都会被记录吧？因为我发现现在已经记录了7跳了，短短8分钟”
- “对，现在首要的问题就是记得太频繁了。但是handoff的问题在于，只要我不主动handoff，就不会记。对吧？这变成俩极端了”
- “我同意旁路模型这个路线。现在的路线记得太多了，会造成混乱”

两个极端的根子是同一件事：没人知道哪个回合是最后一个。cairn 现在的办法是把每个回合都当成最后一个，让会话里的 agent 每回合写一次（D6），结果是记得太勤。调研里唯一不需要知道“哪个回合是最后一个”的做法，是程序读会话内容、另一个模型事后提炼。

用户 10-13 把痛点说成两样，两样都要解决：

- “存的太频繁会导致两个问题，1: cairn的记录太多 2: 存的太频繁会造成模型存这个的也频繁感觉会耗费模型token也会感觉变慢。”

## 3. 做成什么样（草案）

### 3.1 一个会话一份摘要

- 摘要就是现在的“记录”：正文仍是 `docs/DESIGN.md` §6.3 的六节，来源仍是“agent 种类 + 会话 ID”。多记一项“谁写的”：旁路模型、会话里的 agent，或用户。
- 同一个会话再写一次摘要，算这份摘要的新版本。列表和注入只显示最新版，旧版留着可查。存储仍然只追加。

### 3.2 什么时候写

实测（第 6 节）之后改成这样：**谁要读，谁触发。默认在下一个会话开局时写。**

- 同一条工作线上有新会话开局时，cairn 找出记录比摘要新的那些会话（上一个会话、还开着的别的会话），当场调旁路模型写摘要，写完再注入。
- 一个机制管所有情况：正常退出、`corral stop`、崩溃、被强杀、一直开着没关的会话，都一样。它不依赖会话结束的事件，也不需要后台进程。
- 代价：开局后的第一条回复要多等一份摘要的时间（实测 9 到 30 秒）。没有人开新会话，就一直不写。
- 另加一条用户命令（比如 `cairn summarize`），想提前写时手动触发。别的程序轮询 `cairn show` 这类只读命令**不**触发写摘要。
- 不再按回合写，也不按时间或回合数提醒（后者以前否决过，见 `docs/背景与决策记录.md` §3.5）。

为什么不放在会话结束时写：实测里 Codex 被 `corral stop` 关掉时没有会话结束事件，两家被强杀时都没有，而 `corral stop` 是用户平时关 agent 的办法。会话结束时由后台写、或者会话安静几分钟后由后台写，实测证明做得到，留作以后的加速手段（第 7 节第 3 问）。

### 3.3 读什么

- 只读工具已经写在磁盘上的会话记录，路径用 hook 输入里的 `transcript_path`。cairn 不另存对话原文，只存摘要、每个会话的记录路径和“读到哪了”。
- 只读已采用项目里的会话。设了 `CAIRN_DISABLE=1` 的会话不读（派出去的 agent 照旧不进 cairn）。
- 交给旁路模型的是抽出来的文本：用户说了什么、助手答了什么、调了哪些工具。大段的工具输出截短。

### 3.4 旁路模型从哪来

- 调用户已经登录的 `codex exec`，只用这一家，不用 Claude（S4）；不做成可配置的命令。不用另配 API key，cairn 自己不写联网的代码，像调 `git` 那样调一条带超时的命令。
- Claude Code 的会话也由 Codex 写摘要：这些会话的对话内容会交给 Codex。
- 旁路调起来的也是一个会话，实测里它照样触发所在目录的 hook。所以三件事一起做：带 `CAIRN_DISABLE=1`（cairn 的 hook 认这个变量）；在一个没有项目 hook 的临时目录里跑；带上不留会话的参数（`--ephemeral`）。
- 摘要写不出来（额度用完、命令不存在、超时、会话记录解析不了）：不重试个没完，记下“没写成”这个事实，注入时照 D8 只报观测到的，比如“上一个会话有 N 个回合没有摘要”。

### 3.5 会话里的 agent 还存不存

- 每回合的强制确认取消，不再续跑。注入抬头里的“接续约定”那一段删掉。
- `cairn save` 命令留着，变成自愿：用户或 agent 想明确留一句话时用。它和旁路摘要怎么并存，见第 7 节第 2 问。

### 3.6 注入怎么变

- 抬头只留第一句（记录是历史，不是指令或授权）。
- “用户原话”一栏改由旁路模型从会话记录里摘原话，标注改成“由模型摘录，可能断章”。
- 同一条工作线上多个会话的摘要怎么排、“取代”还要不要，见第 7 节第 5 问。

## 5. 新的风险（草案）

| 风险 | 说明 | 打算怎么对付 |
|---|---|---|
| 隐私面变大 | cairn 读对话全文，并交给一个模型 | 只读已采用的项目；原文不入库。Claude Code 会话的内容会交给 Codex，这是多出来的一方 |
| 摘要带进敏感内容 | 对话里出现过的密钥、私人信息可能被写进摘要 | 给旁路的要求里写明不抄密钥；`cairn delete` 照旧可用。只能减轻 |
| 额度 | 每个会话多一次模型调用，长会话输入大 | 用 Codex 的便宜档；工具输出截短；实测量开销 |
| 开局变慢 | 第一条回复要多等一份摘要的时间，实测 9 到 30 秒 | 设时限，超时就先注入已有的；见第 7 节第 4 问 |
| 旁路模型被带偏 | 会话记录里有网页、文件内容，里面的话可能被写进摘要 | 摘要仍只是历史（D7）。cairn 判断不了内容真假 |
| 会话记录格式会变 | 两家各一种格式，随版本变 | 解析不了就不写摘要，照实报；每家一个薄的解析器 |
| 同时写 | 两个新会话同时开局，给同一个旧会话各写一份 | 同一个会话同时只让一个写，另一个等它或直接用已有的 |
| 旁路写得不如在场的 agent | 旁路没在场，只能从记录判断什么重要 | 试点里对比；agent 仍可自愿 `cairn save` |

## 6. 实测回答了什么（P1-04）

报告：`docs/调研/旁路摘要可行性实测.md`。Claude Code 2.1.296、Codex 0.162.1，本机，合成样本，每种情况一两个样本。

| 问题 | 结果 |
|---|---|
| 会话记录拿不拿得到 | 拿得到。两家的 hook 都给路径，文件都是一行一条 JSON，用 `jq` 能抽出“用户说了什么、助手答了什么、调了哪些工具” |
| 回合结束那一刻记录全不全 | Codex 全。Claude 缺最后那条回答，约 120 毫秒后才有 |
| 退出之后最后一个完整回合在不在 | `/exit`、`corral stop`、强杀三种都在（强杀是在回合结束之后杀的，回合中途没测） |
| 有没有会话结束事件 | Claude 的 `/exit`、`corral stop` 有，强杀没有。Codex 的 `/exit` 有，`corral stop` 和强杀没有 |
| hook 里起的后台进程活不活得过会话退出 | 活得过，三种退出方式都是。用的是显式脱离的写法，别的写法没测 |
| 调已登录的 CLI 写摘要 | 走得通，不用配 key。`codex exec`（轻档）两次 28、30 秒；`claude -p`（haiku）一次 9 秒。都写出了六节齐全的摘要 |
| 旁路会不会自己触发自己 | 会。旁路会话照样触发所在目录的 hook，`CAIRN_DISABLE=1` 和不留会话的参数都拦不住，得 hook 自己认这个变量；换到没有项目 hook 的目录就不触发 |
| 会不会留下一堆会话 | 两家都有不留会话的参数，用上之后摘要照常写得出。别处还留不留痕迹没查 |
| 开销 | 十回合的 Codex 会话：记录 279 KB，抽成文本 4 KB，摘要 763 字节。`codex exec` 报的输入约 2 万 token，大头是 CLI 自带的上下文，不是对话 |

没测的：上下文压缩之后、恢复和分叉的会话、带图片的、很长的会话、额度用完时、摘要写得好不好。回合中途被杀 10-13 补测了，见下。

**P1-05 补测（10-13）**：报告 `docs/调研/回合中途被杀的会话记录实测.md`。两家各一个测试会话，一个回合 16 步、做完第三步时强杀。

- 杀之前做完的步骤（工具调用、结果、助手说的话）都在会话记录里，文件末行是完整的一条 JSON。
- Codex 最后一步的输出只出现在 `event_msg` 这一类行里，P1-04 那个抽取脚本不看这一类，漏了它。正式的解析器要把这一类算进去。
- 被杀时没有 Stop、SessionEnd。所以会话记录的路径不能等到 Stop 才记，回合开始时就要记下。
- 每家只有一个样本，杀的时点都在一次工具调用刚结束之后；助手正在生成文字时被杀会留下什么，没测。

## 7. 要用户定的问题

按重要程度排。七问用户 10-13 都定了，结果见第 2 节 S3、S4、S6–S9；下面留着当时的问法和主控的建议。

1. **旁路模型从哪来？** 用户 10-13 定：只用 Codex，调已登录的 `codex exec`；不做“配 API key”这一种，也不做成可配置的命令。
2. **`cairn save` 留不留？** 主控建议：命令留着、注入里不再要求 agent 用。agent 或用户手动存的那条，算这个会话摘要的一个版本，旁路之后再写时把它当输入。
3. **什么时候写？** 主控建议：下一个会话开局时写（3.2 节），先只做这一种。备选是让后台在会话结束时或安静几分钟后写：开局不用等，但要管后台进程，一个长会话会写很多次。
4. **开局多等 9 到 30 秒，接受吗？** 这是第 3 问那个建议的代价。等的长短看旁路用哪家：实测 `codex exec` 轻档约 28 秒，`claude -p` 的 haiku 约 9 秒；Claude 的额度紧。用户 10-13 定了只用 Codex，等得烦了加后台。超过时限（比如 60 秒）就不等了，先注入已有的，并注明“上一个会话的摘要没写成”。
5. **多个会话的摘要怎么排，“取代”还要不要？** 主控建议：同一条工作线上按时间给最近几个会话的摘要，更早的只列一行；“取代”先留着不用，试点后再看删不删。
6. **现有的记录怎么办？** 主控建议：留着，照旧显示，不迁移。
7. **和记忆系统草案的先后？** 主控建议：先做这一件；长期条目往后放，到时候也可以由旁路模型提炼。
