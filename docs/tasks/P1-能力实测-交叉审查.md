### 逐条意见

1. **必须改：幂等边界要覆盖整个收取结果，不能只去重 records。**
   - 位置：`docs/DESIGN.md` §6.2（159–168 行）、§6.5（222–225 行）、§8.2（274–281 行）。
   - 问题：两个 hook 都读到同一文件，A 提交记录和确认后，B 的 records 插入冲突被忽略，但按现有步骤仍会插入新的 confirmations；该表只有自增主键，没有暂存 ID 唯一约束。`--nothing-new` 没有明确的持久去重载体，拒收分支也会重复追加 save_rejected。进程在提交后、删文件前退出，会产生同样的重放。若重放时项目已 unadopt 或取代对象已删除，先重新校验还会把原来已成功的文件记成拒收。只保证“一条 records”不足以保证整个操作幂等。
   - 改法：为每个暂存操作明确稳定 ID 和持久处理结果，覆盖正文、nothing-new、拒收三条路径；在同一事务中先判已处理，再做依赖数据库状态的校验、来源解析和全部写入。已处理直接按既有结果清理，不重复确认、拒收或分配来源。项目采用状态和取代对象校验也要与写入处于同一事务，避免校验后、写入前并发 delete/unadopt 改变条件。只在事务成功后删除；另一个收取者已经删掉文件属于正常竞争。

2. **必须改：未校验的暂存文件不能直接成为 confirmed。**
   - 位置：`docs/DESIGN.md` §6.5（221 行）、§8.3（289、297–300 行）。
   - 问题：收取每次有 50 个文件或 300 ms 的上限，而随后仅按来源和窗口把剩余文件算确认。具体反例：本回合的文件排在第 51 个，正文合格但 supersedes 指向未注入的记录；本次收取没处理它，TurnEnded 却记 confirmed 并放行；下一次收取才拒收、删文件，此时原回合已经结束，失去了改正机会。数据库忙时也不能从“文件存在”推导出“已符合入库规则”。这会把实际拒收的回合误记为已确认。
   - 改法：只有完成所需校验并有可靠处理结果的操作才能写 confirmed。最小方案是只认已提交的 confirmations；忙、超时或预算耗尽时按现有失败放行规则保留文件，并记为未知/待处理，不能伪记确认。若保留暂存态优化，须单列待处理状态及后续拒收的结算规则，不能与 confirmed 混用。

3. **必须改：暂存区必须与目标状态库隔离。**
   - 位置：`docs/DESIGN.md` §6.1（122、127 行）、§6.5（210、216、221、224 行）。
   - 问题：数据库按 XDG_STATE_HOME/HOME 定位，暂存区却是同一 uid 下固定的 `cairn-spool/`，文件不带目标库身份，收取者又处理全部文件。状态库 A 的 save 留下待收文件后，用隔离 XDG_STATE_HOME 的状态库 B 执行命令，会把 A 的文件按 B 的采用状态处理：未采用就拒收并删除，恰好采用则写进错误的库。项目要求的隔离测试同样可能碰到这个问题；不需要多个用户或多个机器即可触发。
   - 改法：用规范化的目标状态目录/数据库路径为暂存区分命名空间，并在格式中携带可核对的目标身份；save 和 hook 使用同一定位规则。收取者只处理自己的命名空间，对其他库的文件不读取正文、不拒收、不删除。这不要求 save 打开数据库。

4. **必须改：禁用和未采用的检查要早于收取。**
   - 位置：`docs/DESIGN.md` §2 D5、§8.1（254–255 行）、§8.3（289–290 行）。
   - 问题：TurnEnded 的第 0 步先收取全部文件，第 1 步才检查未采用和 CAIRN_DISABLE。即使本会话显式禁用，仍会入库、记拒收和删除暂存正文；未采用项目的 Stop 也会触发这些副作用。这违反 D5 的“不检查、不保存”，也使环境禁用不能关闭本次 hook 的处理。SessionStarted 与 TurnEnded 的采用检查顺序还不一致。
   - 改法：统一在 hook 入口先处理禁用，再判断当前项目是否采用，通过后才收取、记事件或渲染。用户显式执行的命令是否收取，仍按用户命令规则处理，不借 hook 绕过这一早退边界。

5. **必须改：属主和权限检查不足以限定文件操作范围，须明确拒绝链接。**
   - 位置：`docs/DESIGN.md` §6.5（209–225 行）、§12。
   - 问题：现文只检查已存在目录的属主和权限，未要求它本身不是符号链接，也未约束待收文件类型。一个指向当前用户其他 0700 目录的 `cairn-spool` 符号链接，若按跟随链接的 stat 检查，完全满足现有条件；收取者随后会解析并删除那个目录中的 `.json` 文件。单个 `.json` 链接也可能使 hook 读到暂存区外的内容；`.tmp` 若跟随预先存在的链接打开，则会覆盖其他文件。仅靠扩展名和 ULID 不构成文件访问边界。
   - 改法：明确安全打开协议：取得可信临时根后，拒绝 cairn 子目录及收取条目的符号链接，核对当前 uid、权限、普通文件类型；相对已打开目录句柄操作，避免检查后再按任意路径打开的竞争。临时文件独占创建、不跟随链接，发布不得覆盖既有操作，文件名 ID 与内容 ID 一致；清理只操作已验证的条目。TMPDIR 回退也须满足同样的可信根条件，否则报错。无需把合法的 macOS 系统路径别名一概当作不安全。

6. **建议改：限定“拒收后告知模型”的承诺，保持最多续跑一次。**
   - 位置：`docs/DESIGN.md` §8.2（283 行）、§8.3（291、298–300 行）、§14 R9。
   - 问题：正文承诺“本回合的 TurnEnded 会把拒收原因放进续跑请求”，但首次 Stop 请求续跑后，模型在续跑里 save 才被拒收时，continued 分支必须直接放行；同窗口另有有效确认时也不会进入附带拒收原因的分支。因此告知不是无条件发生，现有最多一次规则本身应保留。
   - 改法：改成“尚有一次续跑机会且没有有效确认时，随请求告知”；续跑内拒收、预算延迟到以后才拒收等情况只留下无正文的拒收/未确认结果，由 status 或后续正常注入呈现。不为修复提示再续跑第二次。
