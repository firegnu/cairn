# 会话接续的写入时机

调研日期：2026-10-12。范围：公开文档、公开源码和公开 issue；没有安装、运行这些项目，也没有读取本机任何真实会话或记忆数据。

**结论：别家也有这个问题，但并不都在“每回合写完整交接”和“结束前想起来才写”之间二选一。** 本轮看到三种中间做法：程序持续留原始材料、模型隔一段再提炼；同一会话持续更新一份摘要；按任务进展更新同一个工作项。它们分别减少模型调用、可见记录数量、或对会话结束时刻的依赖。最接近“两头兼顾”的具体例子是 Mem0 coding 插件的批次/闲置刷新、Zep 的增量 thread summary，以及社区 handoff 工具的逐回合原始备份加事后重建；但本轮没有找到“任意时刻突然中断仍保证最新语义状态完整，并且低频保存、低成本、不读对话”的证据。这个结论是对下面已读材料的比较，不是运行实测结论。（依据：[Mem0 插件](https://docs.mem0.ai/integrations/claude-code)、[Zep thread summary](https://help.getzep.com/thread-summaries)、[handoff 参考文档](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/docs/reference.md)；查看：2026-10-12。）

## 1. 比较口径

本报告把三个动作分开：“采集”是保存消息、工具结果等原始材料；“提炼”是让模型形成工作状态或知识；“呈现”是新会话实际拿到哪些内容。频繁采集不等于每回合都让主 agent 写交接，更新同一份摘要也不等于只计算一次。“不漏”还要区分已完成回合、进行中的尾部、完整原文和摘要里的关键决定。下文的“推断”只说明这些机制的边界，不把存在恢复命令等同于断电零丢失。

标记约定：**已查证**表示直接打开文档或读取公开源码；**用户报告**表示 issue/讨论里的陈述，未在本轮复现；**推断**表示根据已查证机制作出的判断；**未知**表示本轮没有找到足够依据。各处链接均在 2026-10-12 查看；明确给出的旧文章日期用于区分历史背景和当前实现。源码链接尽量固定到本次读取的提交，不把 README、插件说明和当前代码默认为同一版本。

## 2. 原生 agent：通常先保留会话，再处理上下文和长期记忆

### 2.1 Claude Code

**已查证：** 原生会话在工作过程中把消息、工具调用和结果保存为 JSONL；恢复原会话继续写同一个会话，fork 则产生新会话。上下文接近容量限制时会清理旧工具输出并压缩，也能手动 `/compact`。这提供的是原会话恢复和上下文摘要，和 auto memory 中的偏好、经验等长期内容分开；后者不能视为每回合必有的“停在哪”交接。（来源：[工作原理](https://code.claude.com/docs/en/how-claude-code-works)、[memory](https://code.claude.com/docs/en/memory)；查看：2026-10-12。）

**推断与未知：** 原始会话保存由程序承担，不要求 agent 临终前再写文件；压缩仍需模型处理已有对话，并可能丢细节。恢复时面对的是一个持续增长的会话，不是每回合新增一张交接卡。本轮未查到最后一次写盘的崩溃一致性保证，也未核定完整历史的自动清理规则，因此只能说“已保存部分可供恢复”，不能说“关窗口必然不漏”。（依据：[工作原理](https://code.claude.com/docs/en/how-claude-code-works)；查看：2026-10-12。）

**用户报告与回应：** #11455 的讨论中，2026-09-12 有用户报告即使给了交接常驻指令，额度耗尽也会在任务中途发生，来不及交接。该 issue 于 2025-11-12 提出，曾由作者关闭后重开；所读页面没有给出 Anthropic 已实现自动终止前交接的结论。它证明有人遇到“结束不可预知”的痛点，不能证明原始会话也丢失。（来源：[#11455](https://github.com/anthropics/claude-code/issues/11455)；查看：2026-10-12。）

### 2.2 Codex

**已查证：** CLI 可以按 ID/名称或 `--last` 恢复保存的聊天；fork 保留原始对话并分支，另有归档、取消归档和删除会话。`/compact` 压缩当前上下文。这些是原生聊天接续能力，不依赖用户另写 handoff。文档没有在这些命令说明中承诺进程骤停时最后一段必然已落盘。（来源：[开发者命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli)、[斜杠命令](https://learn.chatgpt.com/docs/reference/slash-commands)；查看：2026-10-12。）

**已查证：** 当前 local memories 文档说明该能力默认关闭；启用后，后台处理会跳过仍活跃或过短的聊天，等空闲足够久再处理，而非每次结束立刻运行。接近额度限制时可能跳过后台任务；提取和整合有分别的模型设置。其产物包括摘要、持久条目和支持证据，处理对象包含过去聊天内容。（来源：[Memories](https://learn.chatgpt.com/docs/customization/memories)；查看：2026-10-12。）

**推断与未知：** 这是“先有历史、稍后后台提炼”的路线，减少主 agent 当回合的保存负担，但新产生的信息不保证立即进入记忆。原聊天的恢复入口和后台记忆不是同一个东西。所读文档未给出精确空闲阈值、每次摘要覆盖/追加规则或完整淘汰算法；本轮也未找到足以归因到这种写入节奏的用户报障与明确修复，不能据此说无人漏记。（依据：[Memories](https://learn.chatgpt.com/docs/customization/memories)、[开发者命令](https://learn.chatgpt.com/docs/developer-commands?surface=cli)；查看：2026-10-12。）

### 2.3 Gemini CLI

**已查证：** 官方明确说明交互期间自动在后台保存，内容包括提示词、回答、工具输入输出、token 统计及可用时的思考摘要；中断后可恢复原 session。列表按会话展示，不把每条消息列成新会话；支持手动命名保存和删除。默认保留 30 天，最大数量限制可配置，但默认不设数量上限，文档里的示例数量不是默认值。`/compress` 则把当前聊天上下文替换为摘要。（来源：[session management](https://geminicli.com/docs/cli/session-management/)、[commands](https://geminicli.com/docs/reference/commands/)；查看：2026-10-12。）

**推断与未知：** 它降低的是忘记手工保存的风险，代价是程序频繁保存完整内容，以及恢复/压缩时的上下文成本；不是每回合请主模型写一条交接摘要。文档没有给出任意写盘中断的零丢失证明。（依据：[session management](https://geminicli.com/docs/cli/session-management/)；查看：2026-10-12。）

**用户报告与回应：** 2026-05-22 的 #27368 报告 Windows、v0.43.0 下 resume 后近期聊天消失；评论提出重名文件或清理有关的解释。页面显示仍开放、被标为 p1；本轮未读到确认根因和已发布修复。因此“自动保存”有实际故障报告，评论的因果分析不能当作本轮源码验证。（来源：[#27368](https://github.com/google-gemini/gemini-cli/issues/27368)；查看：2026-10-12。）

## 3. 显式记忆和任务状态：减少无意义保存，仍依赖模型判断

### 3.1 Engram：提醒有节流，但不等于自动生成交接

**已查证：** README 要求 agent 选择有意义的知识保存，不保存每轮闲聊和原始工具噪声；结束前调用 `mem_session_summary`，压缩恢复后也要求先补摘要。这些文字是给使用该工具的 agent 的行为指令，本身不是强制执行的计时器。（来源：[README / For Agents](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/README.md)；查看：2026-10-12。）

**已查证，核实主控线索：** 当前 Claude 插件挂了 `UserPromptSubmit`、`SessionStart` 的不同场景、`SubagentStop` 和 `SessionEnd`，没有“主 agent 每次 Stop 必写摘要”的路径。`SessionEnd` 脚本向 `/sessions/{id}/end` 发空 JSON 并尝试同步，不调用模型生成交接。此前插件说明里的“只记日志”不能概括当前源码：当前确实会标记会话结束，但仍不负责补齐语义摘要。（来源：[hooks.json](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/hooks/hooks.json)、[session-end.sh](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/scripts/session-end.sh)、[插件说明](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/docs/PLUGINS.md)；查看：2026-10-12。）

**已查证：** `UserPromptSubmit` 会把符合条件的人类提示词送入捕获流程，过滤空输入、任务通知等。在通常的 jq 分支，保存提醒看距最近项目 observation 的时间；没有 observation 时参考真实 session 年龄。达到 900 秒后才有资格提醒，另有默认 900 秒冷却，避免“没有值得存的内容”时每个消息都提醒。检查依附下一次提示词到达，不是闲置到点自己写摘要；Windows Git Bash 的降级路径会跳过这些捕获/提醒。源码还以 `created_at` 排序，因此不能将该条件简单写成“任何记忆更新后重置的严格十五分钟定时器”。（来源：[user-prompt-submit.sh](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/scripts/user-prompt-submit.sh)；查看：2026-10-12。）

**已查证：** 长期条目可用稳定 `topic_key` 更新；但当前 `mem_session_summary` 走 `AddObservation(type=session_summary)`，不设置同一个覆盖用的 TopicKey。所以同会话不同摘要通常新增 observation，并非自动覆盖一份 session 摘要。store 有默认 15 分钟的相同内容去重，不能反过来说每次调用必增一条。摘要可作为记忆查询；本轮未确认摘要专属的自动淘汰周期。（来源：[摘要 handler](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/internal/mcp/mcp.go)、[store](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/internal/store/store.go)；查看：2026-10-12。）

**推断：** 提醒把“纯靠想起来”推进了一步，但模型还要在当前回合决定内容、调用工具；它没有替代最后一段工作状态的生成。突然退出前尚未保存的理解仍可能缺失，已经捕获的用户提示词也不能代表工具执行结果和下一步。其成本是主 agent 的保存调用、提醒上下文，以及插件对部分真实提示词的捕获。（依据：[提醒脚本](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/scripts/user-prompt-submit.sh)、[结束脚本](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/scripts/session-end.sh)；查看：2026-10-12。）

**用户报告与回应：** #515 明确讨论 OpenCode 不能只依赖 agent 自己记得保存，后来由 #516 关闭。#668 报告时区和“尚无第一条 observation”导致提醒不发或太勤；本次读到的源码已有 UTC 日期处理和无 observation 的年龄分支，但本轮没有确认它们在哪个发布版生效。提醒本身也有“太勤/不发”的工程问题，不能只看 README 的节制口号。（来源：[#515](https://github.com/Gentleman-Programming/engram/issues/515)、[#668](https://github.com/Gentleman-Programming/engram/issues/668)、[当前所读脚本](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/scripts/user-prompt-submit.sh)；查看：2026-10-12。）

### 3.2 beads：把“停在哪”放进持续更新的任务

**已查证：** 当前 `bd prime` 给 agent 的协议要求创建任务、开始时标记进行中、更新进展并在完成时关闭；结束前还有检查清单。它保存的核心是任务 ID 对应的状态、依赖和备注，不是每回合生成新的 session handoff。`bd update` 更新原工作项，备注支持追加；长期 `bd remember` 又是另一类内容。（来源：[prime.go](https://github.com/gastownhall/beads/blob/b630f96f5bd231ff7aea78af0d47b6038f228d00/cmd/bd/prime.go)、[README](https://github.com/gastownhall/beads/blob/b630f96f5bd231ff7aea78af0d47b6038f228d00/README.md)；查看：2026-10-12。）

**已查证：** 当前 Claude 设置代码使用 `SessionStart` 的 `bd prime --hook-json` 注入已有工作信息，说明 compact 后也会触发 SessionStart，因而移除了重复的 PreCompact prime。这里的 hook 是重新提供已存状态，不能写成“压缩前自动捕获当下全部进展”。当前/旧任务通过任务查询、状态和关闭操作管理；本轮未核定备注历史的自动清理策略。（来源：[Claude setup](https://github.com/gastownhall/beads/blob/b630f96f5bd231ff7aea78af0d47b6038f228d00/cmd/bd/setup/claude.go)、[prime.go](https://github.com/gastownhall/beads/blob/b630f96f5bd231ff7aea78af0d47b6038f228d00/cmd/bd/prime.go)；查看：2026-10-12。）

**推断：** 这种按进展更新同一任务的方法减少重复交接卡，已写入的任务不随聊天消失；但新发现若还没写进任务，突然结束仍会漏。所查保存路径不必读取 transcript，由 agent 主动提供状态和备注，成本主要落在主 agent 的工具调用上；没有看到“每 N 回合必补当前状态”的保证。（依据：[prime.go](https://github.com/gastownhall/beads/blob/b630f96f5bd231ff7aea78af0d47b6038f228d00/cmd/bd/prime.go)；查看：2026-10-12。）

**用户报告与回应：** 2026-01 的讨论 #848 中，用户称 agent 仍写很多 Markdown，回项目时仍不够了解情况。社区回复先排查 agent 是否真正收到使用 beads 的指令；所读内容不是维护者已修复“自动漏记”的证明。这是指令与使用流程的实际摩擦，也不能据此推断 beads 数据库丢记录。（来源：[讨论 #848](https://github.com/gastownhall/beads/discussions/848)；查看：2026-10-12。）

## 4. 自动后台处理：省的是前台负担，不一定省记录和模型调用

### 4.1 Claude-Mem：每次 Stop 提交摘要工作，另一个模型来做

**已查证：** 当前 hooks 将提示词初始化、工具成功/失败后的 observation、Stop 时 summarize、SessionEnd 时的 session-end 处理分开。worker 负责模型处理，支持不同模型后端。因此用户不用记得 handoff，但 Stop 的摘要机会仍接近每个正常回答一遍，只是没有让主 agent 自己写。（来源：[hooks.json](https://github.com/thedotmack/claude-mem/blob/356b7c08f64c29f931171e264e848772a039da62/plugin/hooks/hooks.json)、[架构](https://docs.claude-mem.ai/architecture/overview)；查看：2026-10-12。）

**已查证：** 数据库将 observations、user_prompts 和 session_summaries 分开；一个 session 可以有多份 summary，用 prompt_number 区分，字段包括调查、完成和 next_steps。它确实保存工作接续信息，但不是自动更新唯一一张摘要。搜索/查看记录与按时间淘汰是不同问题，本轮未确认摘要默认自动保留期限。（来源：[数据库架构](https://docs.claude-mem.ai/architecture/database)；查看：2026-10-12。）

**已查证与边界：** summarize handler 使用末次 assistant message，缺少时会读 transcript 尾部，还从 transcript 读取模型信息；过滤子 agent 等无须汇总的场景。在本次源码的 worker 模式下，事件先写入 spool，再短暂唤醒 worker，唤醒失败仍可由 watcher/sweep 接手。该事实只支持“已成功落入 spool 的事件可稍后处理”，不支持“Stop 没触发或内容尚未采集也能补回”。它付出对话/工具内容访问与后台模型费用，尚未提炼完时可用摘要也会滞后。（来源：[summarize.ts](https://github.com/thedotmack/claude-mem/blob/356b7c08f64c29f931171e264e848772a039da62/src/cli/handlers/summarize.ts)、[spool-hook-event.ts](https://github.com/thedotmack/claude-mem/blob/356b7c08f64c29f931171e264e848772a039da62/src/cli/spool-hook-event.ts)；查看：2026-10-12。）

**用户报告与回应：** #1314（2026-03）报告旧版把 session-complete 放在 Stop，每回合都结束 worker 会话，导致上下文和摘要问题；维护者通过 #1330 将完成操作移到 SessionEnd。**这不等于取消每次 Stop 的 summarize**，当前 hooks 仍保留它。#4305（2026-10）又报告额度冷却后已结束会话的队列滞留；维护者称 v13.29.0 增加每 60 秒重试 stalled buffers，并将重启后的内存缓冲持久化问题另外跟踪。旧版报告与当前源码的 spool 路径不能混作同一现状。（来源：[#1314](https://github.com/thedotmack/claude-mem/issues/1314)、[#4305](https://github.com/thedotmack/claude-mem/issues/4305)、[当前 hooks](https://github.com/thedotmack/claude-mem/blob/356b7c08f64c29f931171e264e848772a039da62/plugin/hooks/hooks.json)；查看：2026-10-12。）

### 4.2 Mem0 / OpenMemory：要区分记忆 API 和 coding 插件

**已查证：** OpenMemory MCP 的介绍是提供添加、检索、列出、删除记忆的服务和界面，不是某个 coding agent 的会话结束检测器。该介绍发表于 **2025-05-13（超过一年）**，页面标注 2026-08-25 更新。它称存储在本地，但示例又使用模型 API key；不能由“本地存储”推出“提炼不需要模型/不会传内容”。本轮未在该介绍中找到独立的交接摘要周期、骤停兜底或自动清理承诺。（来源：[OpenMemory MCP 介绍](https://mem0.ai/blog/introducing-openmemory-mcp)；查看：2026-10-12。）

**已查证：** 当前 Mem0 Claude Code 插件则确有自动时机：hooks 本地采集主 agent 的提示词、回答、文件变化和简短测试/构建结果，采集不调用模型；每 **5 次完成的交互**批量发送，内容很大时提前发送；**闲置 5 分钟**也刷新，下一次交互重置计时；结束和压缩时补送。分离的后台 worker 可在 CLI 正常退出后继续运行，提炼交给 Mem0。Codex 插件也有采集、Stop 检查和 PreCompact/SessionEnd 刷新；只装 MCP 工具的路径没有这些 hooks。（来源：[Claude Code 集成](https://docs.mem0.ai/integrations/claude-code)、[Codex 集成](https://docs.mem0.ai/integrations/codex)；查看：2026-10-12。）

**已查证：** 本次公开共享核心源码把 evidence 写入本地 SQLite，以 `assistant_stop` 边界组成 checkpoint，避免切开一个完成的交互；默认阈值含 5 次交互、10 条消息和 40000 字符。待发送任务使用磁盘文件，启动时能重新处理过期的 running 标记；发送失败可退回 pending。待处理文件有 7 天过期规则，核心还有最大失败次数后的放弃状态。因此它有补送机制，但并不是永不放弃的无限保证。（来源：[memory_core.py](https://github.com/mem0ai/mem0/blob/b7ad69afda6b6ed030347c66d48a13e4de9dec08/integrations/agent-plugin-core/python/memory_core.py)、[hook_runner.py](https://github.com/mem0ai/mem0/blob/b7ad69afda6b6ed030347c66d48a13e4de9dec08/integrations/agent-plugin-core/python/hook_runner.py)、[flush_worker.py](https://github.com/mem0ai/mem0/blob/b7ad69afda6b6ed030347c66d48a13e4de9dec08/integrations/agent-plugin-core/python/flush_worker.py)；查看：2026-10-12；仅阅读源码，未执行。）

**已查证与推断：** 远端提炼结果按项目/个人知识归类，并带 session 的 run_id；不等于每个 session 有一份完整“未完成事项＋下一步”。当前 Add 文档写的是 ADD-only，不能假定后批自动覆盖前批；批次、知识条目和交接卡是三种计数单位。下一会话有有界检索，减少注入量，但不代表历史存储只有几条。本轮未确认插件的本地 evidence 自动清理周期，也未找到可核对的该批次机制用户报障与修复。（来源：[集成](https://docs.mem0.ai/integrations/claude-code)、[Add 操作](https://docs.mem0.ai/core-concepts/memory-operations/add)；查看：2026-10-12。）

**推断：** 这是本轮最明确的“高频廉价采集、低频模型处理”例子，不依赖知道哪轮最后；代价是保存并处理提示词和回答（文档描述发送前脱敏），外加后台模型和服务。它能缓解漏记与前台太勤，但未触发采集的尾部、机器一同停止、反复失败/过期，以及提炼时没选中的工作细节，仍不在零丢失证明内。（依据：[集成](https://docs.mem0.ai/integrations/claude-code)、[hook runner](https://github.com/mem0ai/mem0/blob/b7ad69afda6b6ed030347c66d48a13e4de9dec08/integrations/agent-plugin-core/python/hook_runner.py)；查看：2026-10-12。）

### 4.3 Graphiti / Zep：底层摄取和 conversation summary 不是一层

**已查证：** Graphiti MCP 通过 add_memory 等入口接收 episode，异步抽取并建立图；它有模型/embedding 成本，处理调用者提交的正文。单有 MCP 并不会自动知道宿主哪轮结束，调用时机由接入方/agent 决定。episode 的新增和图中事实的整合也不是一份“当前任务摘要”的覆盖协议；本轮未确认其 MCP 有专门的会话交接对象或默认保留期限。（来源：[MCP README](https://github.com/getzep/graphiti/blob/main/mcp_server/README.md)；查看：2026-10-12。）

**用户报告与回应：** #1707（2026-07 起）报告 v0.29.3 下 add_memory 已返回“入队”，之后模型抽取失败却未留下可查询的失败结果。后续贡献者区分了故障信号改进与持久队列/重放：前者不等于后者；所读页面仍开放，不能说已完成持久性修复。这里是后台处理漏写的问题，不是模型忘记主动 handoff；本轮没有复现，也没有把讨论引用的旧队列实现认定为今日全部版本现状。（来源：[#1707](https://github.com/getzep/graphiti/issues/1707)；查看：2026-10-12。）

**已查证：** 当前 Zep 文档另有 Thread 与 Thread Summary。应用追加消息后，服务异步、增量更新该 thread 的摘要；每个 thread 有一个当前 summary，可读 `last_summarized_at`，尚未生成时可能返回 404。历史消息和跨 thread 的用户知识图谱与这个摘要分开，摘要可用于检索/上下文。因此它确实能让“多次写摘要”表现为一个持续更新的对象，而不是多条并列交接。（来源：[Threads](https://help.getzep.com/threads)、[Thread summaries](https://help.getzep.com/thread-summaries)；查看：2026-10-12。）

**已查证与边界：** Zep 的 Strands 接入示例默认本地缓冲 5 turns，再异步发往服务；文档特别要求关闭前 flush，因为缓冲到发送前 Zep 还没收到数据。可以设置每 turn 发送。该接入层批次不能当作 Zep 所有客户端的默认值，也不能把服务端摘要增量更新等同于客户端尾部已持久化。（来源：[Strands memory 文档](https://help.getzep.com/strands-memory.md)；查看：2026-10-12。）

**推断与未知：** 单份 summary 解决的是可见条目膨胀，模型调用是否合批、精确触发阈值、旧版 summary 是否可回溯、后台落盘与自动清理策略，本轮未查到完整说明；全文消息进入服务的成本仍在。已上传消息可支持后续处理，但尚未上传的缓冲不能靠服务端补回。本轮未找到直接针对当前 Zep thread summary 频率的用户报障与确定回应。（依据：[Thread summaries](https://help.getzep.com/thread-summaries)、[Strands memory](https://help.getzep.com/strands-memory.md)；查看：2026-10-12。）

### 4.4 Letta Code：持久 agent 加后台整理，不是每个会话一张交接

**已查证：** Letta 把 agent 身份、记忆与 conversation 分开，同一 agent 的不同 conversation 共享记忆。agent 可随工作更新持久内容，用户可 `/remember`；MemFS 用 Git 保留修改历史。后台 dreaming 可按完成的 steps 数或压缩触发，使用另外的 agent 整理，可配置；这省主会话操作但增加模型处理，不是纯程序保存。其 `/doctor` 针对重复/结构问题提供整理路径。（来源：[memory](https://docs.letta.com/configuration/memory)、[conversations](https://docs.letta.com/concepts/conversations)；查看：2026-10-12。）

**已查证与未知：** 当前 README 说明原生 Windows 默认不启用客户端自动 dreaming，手动调用和显式启用另论，不能把后台行为不加平台条件地概括。记忆文件反复编辑、Git 保留历史，与每回合新建摘要不同；历史会话也可搜索。但本轮未确认它有固定的每会话交接 schema、最后进行中步骤的崩溃保证，或完整的会话/记忆自动清理期限。（来源：[当前 README](https://github.com/letta-ai/letta-code/blob/main/README.md)、[memory](https://docs.letta.com/configuration/memory)；查看：2026-10-12。）

**用户报告与推断：** #2666（2026-06）报告本地 backend 创建新 agent 后看不到旧 agent 记忆；发帖者同时称旧文件仍在。所读页面没有确认的维护者修复。这是身份范围/重新连接的问题，不能归因为写得不够勤，也不能将“同一 agent 跨 conversation”宣传扩大为“任何新 agent 都自动获得一切”。已经写进记忆与新会话正确读取，是两道条件。（来源：[#2666](https://github.com/letta-ai/letta-code/issues/2666)、[conversations](https://docs.letta.com/concepts/conversations)；查看：2026-10-12。）

## 5. 专门接续和交接的代表做法

### 5.1 社区 claude-code-handoff：每轮原始备份，较少的精炼交接

这里选取 Sting25/claude-code-handoff，是因为同一项目公开实现了手动交接、自动备份与补救重建三条路径；本轮没有核定它的广泛采用程度，不能把它代表成社区共识。

**已查证：** `/handoff` 由模型写本次决定、悬而未决和下次起点；Stop hook 每回合程序性追加 transcript 增量，用游标避免每次重抄。这一层虽仍“每回合写”，却不是每回合再做一份语义摘要。原始备份需要读对话，包含用户输入及工具内容；脚本在 transcript 缺失时直接退出，没有借末次回答完整替代的兜底。（来源：[命令与参考](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/docs/reference.md)、[handoff_turn_append.sh](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/bin/handoff_turn_append.sh)；查看：2026-10-12。）

**已查证：** 上下文阈值提醒在下一次 UserPromptSubmit 检查，默认 100000 tokens 或窗口的 40% 先到者触发；它是建议，不会强制执行交接。提醒还有按增长量节流的路径，不能称为固定间隔自动摘要。SessionEnd、PreCompact 做机械快照并保留符合条件的已精炼 Notes，不重新推理本次经过。（来源：[参考文档](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/docs/reference.md)、[hooks](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/hooks/hooks.json)；查看：2026-10-12。）

**已查证：** 下一会话可加载 current；无有效 current 时可从历史和原始备份组成标明来源的临时上下文，`/handoff-recover` 再做精炼重建。current 与历史分开，默认保留最近 5 份历史，且文档专门区分精炼记录与占位快照的保留。已有记录的机械快照、历史轮换和模型重建不能统称为“结束时自动写好了交接”。（来源：[恢复与保留规则](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/docs/reference.md)；查看：2026-10-12。）

**推断与未知：** 该方法把“没来得及交接”变成下一次付费重建的机会，主要代价是原始内容备份和恢复时的模型工作。尚未经过 Stop 的尾部、缺失 transcript，仍可能没有备份；未做实测，不能把 best-effort 恢复写成无损。文档描述过阈值/提醒缺失的修正，但本轮没有另行核实相应 issue 的用户原始报告，所以不将其列为独立复现证据。（依据：[原始追加脚本](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/bin/handoff_turn_append.sh)、[参考文档](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/docs/reference.md)；查看：2026-10-12。）

### 5.2 Amp：针对下一件事提炼新 thread

**已查证：** Amp 在 2025-10-23 的 handoff 介绍中，用用户给定的下阶段目标提炼新 thread 的起始提示和相关文件，并允许编辑；当前 Threads 文档仍描述 handoff 到新的聚焦 thread，旧 thread 保留可访问。这不是同会话逐回合追加交接，也不是完全无须模型判断的程序快照。（来源：[Handoff 发布说明](https://ampcode.com/news/handoff)、[Threads](https://ampcode.com/docs/threads)；查看：2026-10-12。）

**推断与未知：** 它较好地控制交接内容和调用次数，但是否开始交接仍靠人或 agent 的显式选择；所读材料未给出意外退出前自动补 handoff 的保证。模型需要看旧会话才能提炼，已保留旧 thread 是后续回查的依据，不能等同于已经有一份最新摘要。本轮未确认旧 thread 自动清理规则，也未找到针对 handoff 时机的可核实故障闭环。（依据：[发布说明](https://ampcode.com/news/handoff)、[Threads](https://ampcode.com/docs/threads)；查看：2026-10-12。）

### 5.3 Anthropic 长运行 agent 工程文章：把进度文件放进每个增量工作段

**已查证：** 2025-11-26 的《Effective harnesses for long-running agents》描述 initializer 建立工作环境，后续 coding agent 每次推进有限范围，留下进度文件和 Git 提交，下次先读已有进展。文章讨论单靠压缩仍会留下半成品和不清楚的交接；它报告的是实验流程与失败模式，没有证明一种通用的突然断电交接机制。（来源：[官方工程文章](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)；查看：2026-10-12。）

**推断与未知：** 此处“每个 session/增量工作段收尾”不能偷换成“每个人类消息后写一次”。同一进度文件持续记录，Git 给出代码版本与历史，成本在执行任务的模型回合中；如果该段在写进度前中断，仍需靠已有文件和提交恢复现场。本轮没有得到它对日常交互式聊天的固定回合阈值或未保存尾部保证，也不把文章自身的实验观察当作用户 issue。（依据：[官方工程文章](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)；查看：2026-10-12。）

## 6. 有没有谁同时顾住“不漏”和“不勤”

**有缓解两端的机制，没有本轮可以证明的无条件两全。** “不勤”如果指不让主 agent 每轮写全文，原生历史保存、后台提炼都能做到；如果指不产生许多可见版本，更新同一对象也能做到；如果指完全不频繁访问对话、不写磁盘、不调用模型，那么上述方案并没有同时给出最新状态零丢失的证明。这是下面各自限定条件的比较，不是性能测量或 cairn 方案。

| 路线与代表 | 减少哪种“勤” | 防漏靠什么 | 仍卡在哪里 / 代价 |
| --- | --- | --- | --- |
| 原生历史：Claude Code、Codex、Gemini CLI | 不必每回合另写 handoff；按会话展示 | 已保存对话可恢复，必要时压缩 | 保存的是消息历史；最后未落盘尾部、压缩遗漏没有无损证明；保留原文。[Claude](https://code.claude.com/docs/en/how-claude-code-works)、[Codex](https://learn.chatgpt.com/docs/developer-commands?surface=cli)、[Gemini](https://geminicli.com/docs/cli/session-management/)（查看：2026-10-12） |
| 节流提醒：Engram | 不是每回合强制摘要 | 在新提示到达且时间条件满足时提醒 | 提醒仍须模型执行；没有下一条提示时不会因此自动补交接。[脚本](https://github.com/Gentleman-Programming/engram/blob/5c4171845958f046968c14d7d57a325eb4a83b7e/plugin/claude-code/scripts/user-prompt-submit.sh)（查看：2026-10-12） |
| 工作项更新：beads | 不因每次变化建立新交接对象 | 把进展逐步写入同一任务 | 未写进任务的发现仍缺失，协议不是强制保存器。[prime](https://github.com/gastownhall/beads/blob/b630f96f5bd231ff7aea78af0d47b6038f228d00/cmd/bd/prime.go)（查看：2026-10-12） |
| 每 Stop 后台提炼：Claude-Mem | 主 agent 不用亲自总结 | hook + worker，已接收事件的 spool | 摘要机会和多份 summary 仍频繁；后台失败/额度限制有代价。[hooks](https://github.com/thedotmack/claude-mem/blob/356b7c08f64c29f931171e264e848772a039da62/plugin/hooks/hooks.json)、[数据库](https://docs.claude-mem.ai/architecture/database)（查看：2026-10-12） |

| 单个增量摘要：Zep | 不展示同会话多张摘要 | 已上传消息后台更新 summary | 前端未发送缓冲仍会漏；省条数不必然省模型调用。[summary](https://help.getzep.com/thread-summaries)、[缓冲示例](https://help.getzep.com/strands-memory.md)（查看：2026-10-12） |
| 原始备份＋事后重建：社区 handoff | 精炼摘要按需要生成 | 每轮程序追加，下一会话重建 | 保留原文；没触发 Stop 的尾部仍有缺口；恢复再耗模型。[源码](https://github.com/Sting25/claude-code-handoff/blob/500ac48a5c118df1141859a870d5b0f902553b07/bin/handoff_turn_append.sh)（查看：2026-10-12） |
| 显式 handoff / 工作段结束：Amp、Anthropic harness | 只在选择的边界写 | 旧 thread、进度文件、Git | 人/agent 仍需及时执行；突然截断可能早于该边界。[Amp](https://ampcode.com/docs/threads)、[文章](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)（查看：2026-10-12） |
