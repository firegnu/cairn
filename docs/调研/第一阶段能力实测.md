## 3. A：SessionStart 与注入预算

### Claude Code

**已查证。** 交互启动返回 `CLAUDE-START-7Q9`；`claude -p` 也返回同一合成口令。随后观测到：

- `SessionStart.source="clear"`，产生新 session_id。
- `SessionStart.source="compact"`，模型返回压缩前刚改入 plan 的 `CLAUDE-COMPACT-2K8`。
- 用明确的会话 ID 恢复后，`source="resume"`，模型返回新口令 `CLAUDE-RESUME-6M4`。保存尝试的失败没有被拿来判定注入失败；另用无工具调用的提示单独验证了口令。

6,000 字符夹具由 60 行带不同口令的中文合成文本构成。逐字符比较显示模型回复 5,999 字符、60 行，与输入仅差最后一个换行符；全部正文字符相等。模型未用工具读取夹具。

证据：`claude-startup-reply.json`、`claude-ni-start.stdout`、`claude-a-6000-compare.json`、`claude-a-compact-reply.stdout`、`claude-a-resume-password-reply.stdout`，以及探针对应 SessionStart 事件。

### Codex

**已查证（交互）。** startup 返回 `CODEX-START-7Q9`；clear、compact、resume 分别有 `source` 字段。compact 的 SessionStart 在下一次用户请求前出现，该请求得到新口令 `CODEX-COMPACT-2K8`；resume 得到 `CODEX-RESUME-6M4`，不是旧上下文里的口令。

handler 设置 `additionalContextLimit: 6000` 时，同一 6,000 字符夹具的全部正文与回复相等，也仅差末尾换行。移除该设置、使用默认预算后，不准模型读取溢出文件，模型只复述出第 1–18、44–60 行的口令；返回数组有 22 个 null，并少了 3 个槽位。非 null 口令均来自夹具。这个结果证明该样例没有完整成为模型可见上下文，不能拿它反推精确截断字符数。

**已查证（非交互）与未知分开：**

1. 项目已受信任但探针 handler 尚未单独信任时，直接 exec 没有该探针 SessionStart 日志，回复 `NO-CONTEXT`。
2. 用户信任 SessionStart handler 后，直接 exec 有该探针事件，但首次仍回复 `NO-CONTEXT`。
3. E 的下一次对照保持 hook 定义不变、换用同源码 release 二进制，并换了合成口令及更明确的复述提示，exec 正确返回 `CODEX-TRUST-LINK-8V2`。

因此，exec 并非已证实不支持注入；第一次“hook 已执行、模型未复述”的原因未知。后一次同时改变二进制构建和提示措辞，不能把恢复归因于其中某一个因素。遵照用户主要使用交互式的反馈，未继续追查这一偶发现象，也未补做 exec 的 6,000 字符对照。

证据：`codex-a-6000-compare.json`、`codex-defaultlimit-compare.json`、`codex-a-compact-reply.stdout`、`codex-a-resume-reply.stdout`、`codex-e-comparison.json`。预算字段是近似 token 阈值，不是字符数；官方定义见 [Codex Hooks](https://learn.chatgpt.com/docs/hooks#large-hook-output)，实际选择依据是本轮 A 的样例。

## 4. B：回合、续跑、中断与重复

两种工具的有效 block_first 样例都有以下顺序：

```text
Claude: UserPromptSubmit(S1, prompt_id=P1)
        Stop(S1, prompt_id=P1, stop_hook_active=false)
        Stop(S1, prompt_id=P1, stop_hook_active=true)

Codex:  UserPromptSubmit(S2, turn_id=T1)
        Stop(S2, turn_id=T1, stop_hook_active=false)
        Stop(S2, turn_id=T1, stop_hook_active=true)
```

**已查证。** 原回合与续跑的 ID 都相同；第二个 Stop 后放行，没有第三次续跑，也没有因这次续跑多一个 UserPromptSubmit。后续新用户提示取得不同 ID。UserPromptSubmit 在这些普通用户回合里标出了起点，且其 ID 可与 Stop 对应。

中断样例在 UserPromptSubmit 已到达、正常 Stop 尚未到达时发送 Esc：

- Claude：对应 P2 没有 Stop。Corral 因未收到结束 hook，一度仍显示 working；不能把这个显示当作模型还在执行。
- Codex：收到 `Interrupt(turn_id=T2)`，对应 T2 没有 Stop；另一次被中断的长复述也有 Interrupt。
- 没有用被拒绝的 sleep 命令证明“运行中的 shell 已被中断”；本项证明的是活动模型回合的中断事件。

**观察边界。** 有效样例未发现同一回调被重复送达。这不是不会重送的证明；没有对真实宿主注入重送故障，去重仍必须由核心唯一键完成。为了独立测 JSON、DONE，实验间归档了探针的 block_first 状态，再开始新对照；不把这种人工重置算作同一回合续跑。

**建议。** 接入 UserPromptSubmit 作为确认窗口起点，保留缺字段时的降级窗口；continued 以 stop_hook_active 为准，不能因为本版本 turn_id 不变就去掉该字段。该标记表示 Stop 续跑，不携带“由哪一个 hook 发起”的身份。

证据：两侧 `*-b-json-*`、`*-g-done-*`、`*-b-interrupt-*` 的命令记录及对应探针事件。错误夹具和人工中断后的残留输入不计入正常回合结论。

## 5. C：写入、权限与来源关联

### Claude Code

**已查证。**

- 交互会话 hook 报告 `permission_mode="auto"`：一次正确的 save --nothing-new 成功落盘、最终仅输出 `{"ok":true}`；恢复会话后另一次正确命令未成功，最终为 `SAVE-FAILED`。默认 auto 不能据此承诺每次免干预。
- `claude -p` 的 CLI 报告 `permissionMode="default"`。Sonnet 调用了正确命令，但 result.permission_denials 记录了拒绝；Opus 常规档复测仍有一条拒绝。故默认权限下的失败不是“轻模型根本不肯调用工具”。
- 添加的唯一规则为 `Bash(/绝对路径/cairn-probe save:*)`。单独的 save --nothing-new 成功；使用 printf 将两行合成正文管道传入 save，也成功，`permission_denials=[]`，最终仅为严格 JSON。
- 同一规则下 heredoc 写法被拒绝。该次后续 nothing-new 成功，但整轮按“两条都成功”要求返回 false；没有把它计作正文传输成功。

经过验证的正文形状：

```sh
printf '%s\n' '## 停点' '合成正文，编号 C-18。' | /绝对路径/cairn-probe save --source claude:synthetic-pipe
```

落盘字段为 `body="## 停点\n合成正文，编号 C-18。\n"`、`nothing_new=false`，路径在实验 XDG_STATE_HOME 下。多次独立非交互调用使用窄规则成功，不需要真实用户批准。没有再开一组带窄规则的交互会话，所以不把这点写成“该配置已经在两种模式下完整验证”。首版传输建议使用 printf 管道，并明确需要 save 的窄权限规则；不依赖 auto 恰好放行，不采用本轮失败的 heredoc 模板。

来源关联：成功的交互 nothing-new 保存了该测试会话的真实 source ID；指定 `--session-id` 的非交互 nothing-new 样例也与 hook 的 session_id 对上。合成正文管道样例只验证 source 参数原样传递，没有验证自动获知当前会话 ID。

证据：`claude-c-valid-*`、`claude-ni-c-default.*`、`claude-ni-c-heavy.*`、`claude-ni-c-narrow.*`、`claude-ni-c-pipe.*`、`state/claude/cairn-probe/saves.jsonl`。

### Codex：默认沙箱

**已查证。** 未传 yolo 或扩大沙箱参数。Luna 与 Astra 的交互实验都实际调用了正确命令，PostToolUse 均返回 `Operation not permitted (os error 1)`，实验状态目录没有保存记录。最终回答均为 `{"ok":false}`。

直接 exec 的启动头明确报告：

```text
approval: never
sandbox: workspace-write [workdir, /tmp, $TMPDIR]
```

Luna 和 Astra 的非交互默认沙箱尝试都只返回 false，输出没有工具调用，因此这两次不能单独证明操作系统执行过写入。沙箱拒绝的直接证据来自上述交互工具返回值。没有申请扩大 writable roots，也没有将数据挪到工作区或 /tmp 来冒充满足仓库外状态存储的条件。

### Codex：用户授权 yolo 后

**已查证。** 新启动参数显式加入 `--yolo`，其余模型和状态目录保持原实验选择。

- 交互 resume：新 SessionStart 给出带当前会话 source 的 save 示例。模型执行后，工具返回 `saved`，状态文件里的 source 等于 `codex:<该 resume 会话的 session_id>`，最终只输出合成口令。
- 非交互：启动头为 `sandbox: danger-full-access`，有真实 shell 调用和 `saved` 返回，最终严格 JSON 为 `{"ok":true}`。
- G 的交互续跑又完成了 save，JSON 与 DONE 输出仍保留。

这证明本轮可行方式是“用户显式选择 yolo 后调用 save”，没有证明默认 workspace-write 可用。yolo 放开的是整个沙箱，不能包装成只给 save 的窄授权。若以后仍要保留默认沙箱，只能另行讨论受限的仓库外写入机制；本轮未实现任何替代传输，没有在回答里加记忆标记。

证据：`codex-c-valid-*`、`codex-c-heavy-*`、`codex-ni-c-default.*`、`codex-ni-c-heavy.*`、`codex-a-resume-*`、`codex-ni-c-yolo.*`、`state/codex/cairn-probe/saves.jsonl`。

第一次 C 提示误带了尾部句号参数，命令返回 unknown save argument；这是夹具错误，修正后才进行上述判定，未将其当作权限失败证据。

## 6. D：SessionEnd

| 路径 | Claude Code | Codex |
|---|---|---|
| 非交互进程正常完成 | 有 SessionEnd，reason="other" | 本轮只持久信任了 SessionStart，其他项目 handler 被跳过；未测到有效的 exec SessionEnd，不判定工具缺此能力 |
| 交互 /exit | 有 SessionEnd，reason="prompt_input_exit" | 有 SessionEnd，reason="other" |

**已查证。** 已测路径中都有完整 JSONL 行落盘。Claude 的一次 corral stop 从命令开始到返回约 0.8 秒，期间完成 SessionEnd 记录；Codex 一次 stop 对应记录的 received_at 比命令开始晚约 32 毫秒，日志最终完整落盘，Corral 总关闭时间约 2.3 秒。后者包含 Corral 的退出等待，不能当作 hook 执行耗时，也不能据 received_at 精确推定写完时刻。

## 7. E：安装位置与信任

### Claude Code

**已查证。** 项目 settings.local.json 的探针 hooks 与 Corral 用 --settings 注入的 hooks 能共存，详见 F。

**建议，未验证安装。** 首版优先考虑用户 settings 的增量合并：现有 settings 路径已完成叠加实测，不必为一个本地二进制增加插件打包。用户级 settings 与插件没有分别安装比较；任务禁止修改真实用户配置，允许的实验注入方式也未包含插件安装，因而不能声称插件不可用或用户级安装已经通过。本结论是工程建议，阶段 3 仍须在隔离 HOME 下验证安装、卸载和备份。

### Codex

**已查证。** 项目信任与 hook 定义信任是两件事。Corral 会话里探针早已执行，但 `/hooks` 仍列出需要 review 的条目，真实配置里最初没有本项目 handler 的 trusted_hash。用户随后在 /hooks 中只信任了本项目 SessionStart handler。

采用直接 exec 验证，未传 `--dangerously-bypass-hook-trust`；经用户授权的 `--yolo` 只改变工具权限/沙箱。三个 fresh session 对照：

| 对照 | hook 文本 | 二进制 | 探针 SessionStart 事件 | 模型结果 |
|---|---|---|---|---|
| 已持久信任的基线 | 原定义，limit=6000 | debug v1 | 有 | NO-CONTEXT；原因未知，见 A |
| 只换固定软链接的目标 | 字节不变 | 同源码 release v2 | 有 | CODEX-TRUST-LINK-8V2 |
| 改 SessionStart command 文本，前加 exec | 改变；语义仍为执行同一个探针 | release v2 | 无 | NO-CONTEXT |

两个二进制 SHA-256 不同；第二步整个 hooks.json 的 SHA-256 与第一步相同。第三步没有重新点信任，原 trusted_hash 保持不变，新的 handler 被跳过。本轮证明的是定义变更使旧信任不再覆盖它，没有实际再信任第三步定义。

实验后已恢复原 hooks.json 字节和指向 debug v1 的软链接，保留 v2 文件供复核；没有编辑真实信任记录。详情见 `codex-e-comparison.json`、`codex-e-baseline-config.json` 和 `trust-after-approval.txt`。该行为与 [Codex 的 hook 信任说明](https://learn.chatgpt.com/docs/hooks#review-and-trust-hooks)一致；结论依据为本轮上述执行对照。

## 8. F：与 Corral 共存

**两种工具均已查证。** 相同测试回合同时有：

- 项目探针自己的 SessionStart、UserPromptSubmit、Stop 日志；
- Corral 公开 status 的 last_event=Stop、state=idle；
- corral reply 返回对应合成口令或严格输出。

例如首次交互启动分别返回 `CLAUDE-START-7Q9`、`CODEX-START-7Q9`。项目 hook 与 Corral 自己的 hook 都工作，没有以项目配置覆盖掉 Corral 的状态通道。证据为 `*-startup-status.json`、`*-startup-reply.json` 以及对应探针日志；没有读取 Corral 事件文件。

Codex 这一结果包含 Corral 自动提供的 hook-trust bypass。它只说明这条启动路线能共存，不等于独立启动的 Codex 已经信任项目 handler，也不等于扩大了工具写入沙箱。

## 9. G：续跑对最终输出的影响

**已查证。**

- Claude 交互：JSON 与两行正文末行 DONE 的样例均保持；probe 的 Stop 从 false 到 true。
